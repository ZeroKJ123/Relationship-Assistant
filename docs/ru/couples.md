# Пары и приглашения

После входа откройте «Мои пары» и пригласите партнёра. Дата начала обязательна и не может быть в будущем по часовому поясу пары. По умолчанию используется Europe/Minsk; принимаются зоны IANA. Дни вместе считаются по календарным датам этой зоны, после завершения счётчик останавливается.

Ссылка действует 7 суток и показывается автору один раз после выпуска. Новая ссылка отменяет предыдущую. Автор может отменить ссылку отдельно. Отмена и истечение срока оставляют ожидающую пару: можно выпустить приглашение снова или завершить её, чтобы принять чужое приглашение.

Получатель сначала входит или регистрируется, затем явно подтверждает принятие. После регистрации профиль показывает резервные коды и ссылку «Продолжить принятие приглашения». Нельзя принять свою ссылку, присоединиться третьим участником или иметь одновременно несколько ожидающих/активных пар. Повторное принятие тем же получателем не создаёт новую запись.

Оба участника равноправны. Любой может завершить пару после отдельного подтверждения. Это освобождает обоих для новой пары и отменяет ожидающие приглашения. История остаётся доступна прежним участникам, включая после создания новой пары. Новому партнёру и постороннему администратору она недоступна. Право `manage-system-settings` предназначено только администраторам и не открывает личные данные.

## Недельный лимит «Очень хочу»

В карточке пары откройте «Наши договорённости». Каждый участник отдельно отвечает, сколько особо желанных просьб он считает подходящим на неделю: от 1 до 14. Ответы видны обоим. После второго ответа предлагается среднее с округлением вверх; например, 3 и 4 дают предложение 4. Даже одинаковые ответы не активируют правило автоматически.

Каждый явно подтверждает одну и ту же версию. До двух согласий `WeeklyLimit::getActiveLimit()` возвращает null, и особо желанные просьбы закрыты. Лимит одинаков для обоих, учёт отдельный для каждого автора; неделя начинается в понедельник по IANA-зоне пары. Отправка «Очень хочу» проверяет квоту и неотрицательный баланс, отказ не возвращает место. Подробнее: [дела и сердечки](hearts-and-duties.md).

Можно отклонить обсуждаемый вариант или предложить другое число. Новый вариант требует двух новых согласий, включая автора. Изменение личного ответа предлагает новое среднее; неизменённый ответ не создаёт лишнюю версию. Запрос со старой версией предлагает обновить страницу. Повторное подтверждение не добавляет второе согласие одного человека. Согласованное правило нельзя отменить односторонне: при обсуждении нового действует прежнее до двух согласий с заменой.

Ожидающие и завершённые пары не могут менять договорённости. История версий доступна прежним участникам после завершения, но не новым партнёрам. Пока пара завершена, её исторический лимит не даёт разрешения на новые просьбы.

## Структура данных

| Таблица | Основные поля и ограничения |
| --- | --- |
| `couples` | `status`: pending/active/ended; `started_on`, IANA `timezone`, `currency`, `ended_at` |
| `couple_members` | Исторический `user_id`, `couple_id`, `slot`: first/second, `joined_at`, `ended_at`; уникальны пара+участник и пара+слот |
| `couple_members.active_user_id` | Уникальное nullable-ссылочное поле. Пока пара ожидает или активна, равно user_id; при завершении очищается, исторический user_id сохраняется |
| `couple_invitations` | Автор/пара, уникальный SHA-256 `token_hash`, pending/accepted/cancelled, срок, получатель и дата принятия |
| `couple_agreements` | Одна запись на пару, текущая версия предложения, nullable активная версия и её недельный лимит |
| `agreement_answers` | Число каждого участника; уникальны договорённость+пользователь |
| `agreement_proposals` | Версия/лимит/необязательный автор/дата принятия; статусы proposed, accepted, declined, superseded; уникальны договорённость+версия |
| `agreement_approvals` | Подтверждения конкретной версии; уникальны предложение+пользователь |

В таблице приглашений нет исходного токена. Случайная ссылка содержит 64 символа; временный показ передаётся зашифрованной flash-сессией, привязанной к паре. Ответы не кешируются; Referrer-Policy: no-referrer ограничивает передачу ссылки через заголовок Referer. Логи содержат технические ID и этап операции без ссылки или личного текста.

Операции выполняются через Actions внутри транзакций. Сначала блокируются пользователи по возрастанию ID, затем пара и приглашение. Проверки повторяются под блокировкой. Ограничения базы поддерживают одну текущую пару на пользователя и два слота на пару. Если состав изменился во время подтверждения завершения, запрос предлагает обновить страницу и подтвердить актуальный состав снова.

Все изменения договорённостей выполняются Actions в транзакциях. Блокировки следуют порядку пользователи → пара → договорённость → предложение/ответы/подтверждения. Для состояния, которое могло измениться во время ожидания, применяются locking reads: обычное чтение в MariaDB REPEATABLE READ может видеть старый снимок. Подтверждения старой версии не переносятся. Логи показывают технические ID, версии и факт активации; личные ответы не записываются.

## Миграция и откат

Миграция `2026_10_09_193842_create_couple_tables.php` добавляет три новые таблицы, не изменяя данные аккаунтов. В рабочую базу она автоматически не применялась. Перед применением используйте обычную процедуру выпуска с проверенной резервной копией. `down()` удаляет эти таблицы: схема возвращается назад, но история и приглашения будут потеряны. Для сохранения данных перед откатом нужна резервная копия и проверка её восстановления.

Миграция `2026_10_09_203000_create_couple_agreement_tables.php` добавляет четыре таблицы договорённостей без изменения прежних данных. Она также не применялась в рабочую базу. При её rollback удаляются ответы, версии и подтверждения: сохранить их можно только заранее подготовленной и проверенной резервной копией. Откат не восстанавливает потерянную историю.

## Проверки

Обычные Pest-тесты используют SQLite в памяти. Отдельные интеграционные тесты запускаются в одноразовой MariaDB 11.4: две попытки разных гостей принять одну ссылку, один получатель с двумя ссылками и повторное принятие одним получателем. Они используют независимые PHP-процессы с общим стартовым барьером. Также проверяются ограничения самой базы. Для договорённостей проверяются одновременные ответы, два подтверждения одной версии, повторное подтверждение одного участника, конкурирующие встречные варианты, подтверждение старого варианта одновременно с заменой и завершающее согласие одновременно с выходом из пары. GitHub Actions выполняет обе группы проверок.

Для запуска и защиты тестовой базы см. [разработку](development.md). Общие [просьбы и условия](requests.md), [дела и сердечки](hearts-and-duties.md) и [Telegram](telegram-and-scheduling.md) описаны в своих руководствах.

## Даты отношений
На странице активной пары можно изменить начало отношений и добавить дату свадьбы. Свадьба необязательна: пустое поле означает, что дата не указана. Обе даты не позже сегодняшнего дня в часовом поясе пары; свадьба не раньше начала отношений. Рядом с числом дней на главной и странице пары показывается календарный срок в годах и месяцах. У завершённой пары срок фиксируется на момент завершения. Поля `couples.married_on` (nullable date) и `dates_version` защищают от перезаписи устаревшей формой. Обе стороны действующей пары могут редактировать даты.
